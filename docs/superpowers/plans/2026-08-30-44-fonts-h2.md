# #44 fonts, direction H2: the per-context filter becomes the only narrowing mechanism

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make `NewContext(os=X)` deliver X's font environment even when the browser was launched for a different OS, without letting any context see a font it was not given.

**Architecture:** Today two mechanisms narrow the font set. `gfxPlatformFontList`'s constructor writes the launch config's `fonts` list into the `font.system.whitelist` pref, and upstream `ApplyWhitelist()` then *deletes* every other family from `mFontFamilies` — a process-wide, launch-time, one-OS decision. On top of that, `FontListManager` filters per user context at a handful of read sites. The first mechanism is why a cross-OS context can never work: the families it wants were deleted before it existed. H2 removes the pref write and makes the per-context filter the sole narrowing mechanism, with the launch-level `fonts` key as the fallback answer for contexts that installed no list of their own (including the default context, id 0).

**Tech Stack:** C++ patches against Firefox 152.0.4 (`patches/*.patch`, applied by GNU patch via `scripts/patch.py`), the `FontListManager` addition, `pythonlib/camoufox`, and the `Smoke Fingerprint` GitHub Actions workflow as the measurement harness.

---

## The trade this plan makes, stated out loud

`ApplyWhitelist()` deletion is a **structural** guarantee: a deleted family is unreachable from every read path, including paths nobody has enumerated. H2 replaces it with **check-at-callsite** enforcement, which is only as complete as the set of gated call sites. This is strictly weaker in kind, and it is chosen deliberately: the structural guarantee is exactly what makes cross-OS contexts impossible, so it cannot be kept and the feature delivered.

The mitigation is the guard, and the guard is therefore sequenced **first**, with the flip last. Two consequences follow and are non-negotiable in this plan:

1. Every read path this plan gates gets a probe that is demonstrated **red before** the gate lands. A gate whose probe was never red proves nothing.
2. The flip (Task 8) does not land until the guard is green on **both** a Linux arm and a native-Windows arm. On Linux the bundled `fonts.conf` excludes host fonts, so a Linux-only measurement is structurally blind to the host-font question the flip raises. (CLAUDE.md, "Verifying spoofing claims", lessons 1 and 3.)

If the Windows arm shows a residual leak that deletion would have bounded, stop and put the choice — H2 vs. a union whitelist vs. an opt-in cross-OS launch flag — back to the human with the run IDs. Do not flip anyway.

```cpp
// Camoufox: per-context font visibility (#44).
//
// A read path with no per-context font list must not answer "allow
// everything". Fall back to the launch-level "fonts" key -- this profile's
// own set -- which is also what the default context (userContextId 0) is
// entitled to see, since nothing ever calls setFontList() on it.
static bool CamouIsFontAllowed(const nsACString& aLowerKey) {
  uint32_t ctx = mozilla::dom::FontListManager::GetCurrentContext();
  if (ctx != 0 && mozilla::dom::FontListManager::HasFontList(ctx)) {
    return mozilla::dom::FontListManager::IsFontAllowed(ctx, aLowerKey);
  }
  static const std::vector<std::string> sLaunchFonts =
      MaskConfig::GetStringListLower("fonts");
  if (sLaunchFonts.empty()) {
    return true;
  }
  std::string key(aLowerKey.BeginReading(), aLowerKey.EndReading());
  return std::find(sLaunchFonts.begin(), sLaunchFonts.end(), key) !=
         sLaunchFonts.end();
}
```

Delete any comment sentence that refers to `fonts:whitelist`; it describes a mechanism this branch does not have.

- [ ] **Step 1: Arm (e) — CSS `@font-face` (`FontFaceSet::InsertRuleFontFace`)**

`FontFaceSet::Check` and `FontFaceSet::Add` scope an `AutoFontListContext`; `InsertRuleFontFace` does not, and a CSS `@font-face` rule reaches `SetStatus` through it during style flush. Probe: inject a stylesheet rule rather than constructing a `FontFace` in JS, then read the resulting entry's status.

The `@font-face` family name must be a **real marker family**, not an invented
one. The fork's `FontFace::Status` / `FontFaceImpl::SetStatus` answer from
`GetFamily()` through `IsFontAllowed()`, so an invented name like `"ProbeE"` is
in no context's list and reports `error` in *every* context — the arm would stay
red after its gate lands and prove nothing.

```js

sheet.textContent =
  '@font-face { font-family: "Segoe UI"; src: local("Segoe UI"); }' +
  '@font-face { font-family: "Helvetica Neue"; src: local("Helvetica Neue"); }';
document.head.appendChild(sheet);
document.body.offsetHeight;              // force a style flush
await document.fonts.ready;
const out = {};
for (const f of document.fonts) { out[f.family] = f.status; }
return out;
```

Verdict: each family's status must match what `measureText` says about that same
family **in that same context** — `loaded` where the context has the family,
`error` where it does not. Pre-gate, `InsertRuleFontFace` runs with no context in
scope, so under the bare launch (no `fonts` key) `IsFontAllowed` falls through to
allow-all and both families report `loaded` while measurement says one of them is
absent. That disagreement is the red.

### Task 3: Fix the quoted family key `InsertRuleFontFace` hands `IsFontAllowed`

**This task's scope changed on Task 2's evidence.** It was written as "scope an
`AutoFontListContext` around `InsertRuleFontFace`". That is not the defect.
Task 2's arm (e) discriminator (run 33388465143) measured:

```
raw families ['"Segoe UI"', '"Helvetica Neue"', 'Tahoma']
mac: Segoe UI='error'  Helvetica Neue='error'  Tahoma='loaded'
win: Segoe UI='error'  Helvetica Neue='error'  Tahoma='loaded'
document.fonts.add(new FontFace('Calibri', ...)):  mac='error'  win='loaded'
```

`Tahoma` needs no quoting in CSS and resolves correctly in both contexts. The two
names containing spaces are serialised by CSS **with quotes** and report `'error'`
everywhere. The `document.fonts.add()` path — same families, no CSS rule — is
per-context correct. So the family key reaching `IsFontAllowed()` from a CSS rule
carries its quote characters, no list entry can ever match it, and every such face
reports `'error'`. A missing context scope would not produce that pattern.

**Verify the mechanism in source before writing the fix.** Follow the family
string from `FontFaceSet::InsertRuleFontFace` to `FontFaceImpl::SetStatus` to
`IsFontAllowed`, and identify exactly where the quotes survive. The fix belongs
wherever the key is built, not as a `Trim('"')` bolted onto the comparison — and
if the same unnormalised key reaches other consumers, say so rather than fixing
only the one this arm measured.

**One thing to check and report, without expanding this task to fix it.** The
fork's `SetStatus` answers from `IsFontAllowed` for *every* `@font-face`,
including ordinary web fonts loaded by URL whose family is in no OS font list at
all. If those also report `'error'`, that is a production-wide surface far beyond
#44 — a page can watch its own web font render while `document.fonts` calls it
failed. Measure it, record the answer on issue #44, and do not fix it here.

### Task 4b: The negative fallback cache this plan just made reachable (#81)

**This is a regression Task 4 introduced, not a pre-existing bug found alongside
it, so it is ours to clean up.** It must land before the flip in Task 8.

`gfxPlatformFontList::mCodepointsWithNoFonts` is a process-wide "no font covers
this codepoint" cache, keyed only by `FontVisibility` and unrelated to
`mUserContextId`. `gfxFontGroup::FindFontForChar` consults it through
`SkipFontFallbackForChar()` at `gfxTextRun.cpp:3450` — **before** reaching
`WhichSystemFontSupportsChar` at `gfxTextRun.cpp:3506`, which is where Task 4's
gate lives. A cache hit skips the gate entirely.

Before Task 4 a fallback miss was almost impossible, because the scan was
unfiltered and nearly always found something. After Task 4 a miss is the correct
and expected outcome whenever a context's list covers nothing for that codepoint.
That is what makes the cache reachable in normal operation for the first time.

Effect: once any context's gated fallback misses, every later context sharing that
`FontVisibility` level gets a false "no font" — including one whose own list would
have served the codepoint, and without its gate ever running. The failure is
one-way: tofu where a glyph belonged, never a font the context was not allowed. So
it is not a leak and not a crash. It is a coherence defect, and for an anti-detect
browser that is the part that matters: the rendered result stops being a function
of the claimed fingerprint and becomes a function of process history.

- [ ] **Step 1: Write the failing measurement first**

The existing guard cannot see this, and the reason generalises: every measurement
gets its own fresh launch, so the cache always starts empty. Every fix made while
building that guard moved toward more process isolation, which is exactly what
hides this — while production runs many contexts in one process, which is the
whole point of the feature.

So the arm must do the opposite of every other arm here: **one launch, two
contexts, in order**. Give context A a list covering nothing for a chosen
codepoint, measure it (miss, poisons the cache), then measure the same codepoint
in context B whose list does cover it. B rendering tofu is the bug. B rendering
its glyph is the fix. Verify the arm is red before writing any fix.

- [ ] **Step 2: Choose among the three candidates on evidence**

Clearing `mCodepointsWithNoFonts` from `FontListManager::SetFontList` is the
smallest and most conservative, costing some redundant fallback work per context.
Keying the cache by user context id is more precise and more invasive. Skipping
the cache whenever a per-context list is active is the bluntest. Which is right
depends on how hot this path is. Measure before choosing, and say in the report
what the cost of the chosen one is rather than asserting it is negligible.

- [ ] **Step 3: Verify, then commit**

Arm goes green; arms (a)-(g) unchanged. Same balanced-hunk and pre-flight rules as
every other patch task here.
