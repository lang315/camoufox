## #97 — `--executable-path` still requires a managed install

### Problem

`pythonlib/camoufox/utils.py:994-997` resolves the Firefox major version from
the managed install unconditionally:

```python
if ff_version:
    ff_version_str = str(ff_version)
    LeakWarning.warn('ff_version', i_know_what_im_doing)
else:
    ff_version_str = installed_verstr().split('.', 1)[0]
```

`installed_verstr()` (`pkgman.py:768`) raises `CamoufoxNotInstalled` when no
managed install exists, regardless of whether the caller supplied their own
binary through `executable_path`. Every other managed-install read on the
launch path is guarded by that path first — `utils.py:71`, `:222-225`,
`:250-257` — so this is the one unguarded read.

Effect: a machine with no `camoufox fetch` install cannot launch a local binary
at all. The service-tester's local-binary phase only worked previously as a side
effect of the fetched phase having populated the cache earlier in the same run.

### Version source

Established empirically against `camoufox-150.0.2-beta.25-mac.arm64.zip` rather
than assumed:

- Packages ship **no `version.json`**. That file is written by the installer
  into `INSTALL_DIR` (`pkgman.py:652`), so `Version.from_path()` cannot read a
  package or a raw build artifact.
- Packages **do** ship `application.ini`, a Gecko invariant generated from
  `build/application.ini.in`. Its `[App]` section carries
  `Version=150.0.2-beta.25`, the same shape `installed_verstr()` returns, so
  `.split('.', 1)[0]` yields the major identically.
- In a macOS `.app` the file is at `Contents/Resources/application.ini` —
  the same directory `properties.json` lives in, which `_load_properties`
  (`utils.py:243-257`) already reaches through an explicit `.app` fallback.

### Fix

1. Add `_bundle_verstr(path: Optional[Path]) -> Optional[str]` to
   `pythonlib/camoufox/utils.py`. It resolves `application.ini` beside the given
   executable, applying the same `Contents/MacOS` → `Contents/Resources`
   fallback `_load_properties` uses, parses the `[App] Version=` line, and
   returns the major. It returns `None` — never raises — when there is no
   executable path, no file, or no parsable version line.
2. At `utils.py:994`, when no explicit `ff_version` was given, try
   `_bundle_verstr(executable_path)` first and fall back to
   `installed_verstr()` only when it returns `None`. A managed launch is
   therefore unchanged, and a local-binary launch never consults the managed
   install.
3. Emit no `LeakWarning`. The value is derived from the binary that is about to
   run, not asserted by the caller, so the warning's premise does not apply.

`service-tester/run_tests.py`, `run_tests.sh` and `run_tests.ps1` are **not**
changed. The issue proposes passing `ff_version` alongside `executable_path`
from the harness; that would trip `LeakWarning.warn('ff_version', ...)` on every
local run. Fixing the root read makes the harness's phase-order dependency
disappear without touching it.

### Verification

- **Red first.** This machine has no `~/Library/Caches/camoufox`, so the issue's
  exact failure reproduces as-is. Run the service-tester local-binary phase
  against a binary and capture `ERROR: Failed to launch Camoufox: official/stable
  is not installed.` with its exit status before changing anything. Keep the
  cache absent for the whole exercise; a `camoufox fetch` anywhere in the loop
  destroys the reproduction.
- **Green after.** Same invocation, same absent cache, passes.
- **Unit test.** `pythonlib/tests/test_bundle_verstr.py`, alongside the existing
  `test_load_properties.py` which covers the same `.app` fallback, run by
  `pytest tests/ -q` as `pythonlib.yml` does. Cases: a flat bundle, a macOS
  `.app` layout, a missing `application.ini`, and an `application.ini` with no
  parsable `[App] Version=` line.
- Binary for the local run: the macOS arm64 artifact from build `34554470815`,
  which is the build the issue was observed on. `~/Downloads/camoufox-150.0.2-beta.25-mac.arm64.zip`
  is present locally but is a different major and sits below the Playwright
  version floor, so it is a fallback only, and a run against it must say so.
- Both suites for the pull request per `CONTRIBUTING.md`, binary permitting.

### Noticed, deliberately not fixed

`warn_if_executable_predates_playwright` (`utils.py:145`) calls
`Version.from_path(Path(path).parent)` with no `.app` fallback and swallows
`FileNotFoundError`. It therefore never fires on macOS, and never fires for any
package at all, since packages carry no `version.json`. Same defect class as
#97, different symptom. Record it in the pull request body; do not change it
here.

## #95 — bundled `Geneva.ttf` never renders

### Root cause

Read from `camoufox-152.0.4-beta.31/gfx/thebes/gfxFontUtils.cpp:414-426`. The
non-`XP_MACOSX` branch of the subtable-acceptance macro is:

```c
#  define acceptableUCS4Encoding(p, e, k) \
    ((p) == PLATFORM_ID_MICROSOFT && (e) == EncodingIDUCS4ForMicrosoftPlatform)
```

Geneva's only cmap subtable is `(platformID 0, platEncID 3)` format 12.
Walking `FindPreferredSubtable` (`:434-522`) with that input:

- `acceptablePlatform(0)` passes — platform 0 is the Unicode platform.
- The format-4 branch does not apply; the subtable is format 12.
- The format-10/12/13 branch calls `acceptableUCS4Encoding(0, 3, 0)`, which on
  a non-macOS build requires `platformID == 3`. It is false.

No branch fires, `keepFormat` stays `0`, and `FindPreferredSubtable` returns 0.
`ReadCMAP` (`:530-556`) then falls through its switch to
`default: return NS_ERROR_FAILURE`, and `gfxFontconfigFontEntry::ReadCMAP`
(`gfxFcPlatformFontList.cpp:486-540`) takes its error path:

```c
// if error occurred, initialize to null cmap
charmap = new gfxCharacterMap(0);
mHasCmapTable = false;
```

The family stays in the font list — so `document.fonts.check()` and any
enumeration report it present — but its character map is empty, so it is never
selected for any text run. That is exactly the reported symptom: advertised,
and pixel-identical to a deliberately absent family.

The `XP_MACOSX` branch of the same macro accepts
`(p) == PLATFORM_ID_UNICODE && (e) != EncodingIDUVSForUnicodePlatform`, which is
why real macOS renders Geneva. The bug is a fidelity gap between a macOS-target
build and a Linux- or Windows-target build, not a corrupt font file.

The `(3, 1)` observation in the issue body is a coincidence, not the cause.
Helvetica Neue's only subtable is `(0, 1)` format 4 and it renders correctly,
because the format-4 branch accepts any Unicode-platform encoding.

### Blast radius

Replaying the real predicate over all 574 faces in `bundle/fonts/` gives seven
dead faces across five families, all in `bundle/fonts/macos/`:

| file | families | subtables |
|---|---|---|
| `Geneva.ttf` | Geneva | `[(0,3,12)]` |
| `Apple Symbols.ttf` | Apple Symbols | `[(0,4,12)]` |
| `LastResort.otf` | .LastResort | `[(0,4,13)]` |
| `STHeiti Light.ttc` | Heiti TC, Heiti SC | `[(0,4,12),(1,0,6),…]` |
| `STHeiti Medium.ttc` | Heiti TC, Heiti SC | `[(0,4,12),(1,0,6),…]` |

`Makefile` ships `bundle/fonts/macos/` in the Linux package
(`package-linux: --fonts windows macos linux`) and the Windows package
(`package-windows: --fonts macos linux`), and not in the macOS package
(`package-macos: --fonts windows linux`). Every package that ships these five
families is a build where the macro rejects them. They are dead in 100% of the
cases where they ship.

All three platform font lists route through the same helper —
`gfxFcPlatformFontList.cpp:508`, `gfxDWriteFontList.cpp:556`,
`CoreTextFontList.cpp:265` — so one macro change covers the Linux and Windows
targets, and the macOS target already takes the permissive branch.

### Fix

A new patch adding one clause to the non-macOS macro:

```c
#  define acceptableUCS4Encoding(p, e, k)                               \
    (((p) == PLATFORM_ID_MICROSOFT &&                                   \
      (e) == EncodingIDUCS4ForMicrosoftPlatform) ||                     \
     ((p) == PLATFORM_ID_UNICODE &&                                     \
      (e) != EncodingIDUVSForUnicodePlatform && !(k)))
```

The `!(k)` term makes the new clause strictly a last resort. A font that has
already had a subtable accepted keeps it, so every font that renders today is
byte-for-byte unaffected; only faces where nothing else was acceptable gain a
character map. That bounds the change to the seven faces above.

Patch authoring follows CLAUDE.md: write it through `make edits`, balance the
context lines in every hunk, and dry-run with the invocation the build uses —

```bash
patch -p1 --forward -l --binary --dry-run < patches/your.patch
```

`git apply --check` is not a valid pre-flight for this repository.

### Alternatives rejected

- **Rewrite the five font binaries** to carry a `(3,10)` format-12 subtable.
  Two are `.ttc` collections with tables shared across faces, the edit is lost
  on any font refresh, it does nothing for the next macOS font of the same
  shape, and `.gitattributes` is `* text=auto`, which makes committing modified
  binaries riskier than committing a text patch.
- **Drop the five families from `pythonlib/camoufox/fonts.json`.** Trades
  "advertised but never renders" for "a macOS profile missing five families
  real macOS has". Both are tells; the second is not obviously smaller.

### Verification

Acceptance is the existing pixel-checksum discriminator in `smoke.yml` flipping

```
Geneva differs from absent-reference (pixels, not width): False -> True
```

with its positive control still reported valid, taken under `FONTCONFIG_FILE`
pointed at the bundle — the font universe the product ships, per CLAUDE.md
lesson 8, not the runner's own fontconfig. Extend the same discriminator to
Apple Symbols, .LastResort, Heiti TC and Heiti SC in the same run so the other
four families are measured rather than assumed.

Requires one `build.yml` run on the branch, then one `smoke.yml` run against
that build's `CamoufoxBuilds-linux-x86_64` artifact.

### Blind spots to state in the pull request

- Measured on Linux only. The Windows target takes the same macro branch and
  the same `gfxFontUtils::ReadCMAP`, so it is covered by reading, not by
  measurement.
- The macOS target is unaffected by construction: it already takes the
  permissive branch, and `package-macos` does not ship these files.

## #44 — re-measure the headline symptom, then close or narrow

### Why a re-measurement and not more gating

The WebGL half's fix is present in `patches/webgl-spoofing.patch` — the
dedicated `UNMASKED_RENDERER_WEBGL` / `UNMASKED_VENDOR_WEBGL` branch at line
376 — and the font rounds landed through PRs #84, #93 and #96. Nothing in the
issue's comment history re-runs the scenario the issue body actually describes
after those landed. The last comment measuring that path found it red.

`smoke.yml` already carries two #44 guards, at line 329 (per-context WebGL
renderer beats the launch config) and line 602 (per-context font list beats the
launch whitelist). Neither drives the pythonlib entry point the issue names.

`service-tester` cannot answer this question either: it deliberately groups
contexts by OS into separate browsers (`run_tests.py:180-200`), which is the
opposite of the mixed-OS-in-one-browser case.

### The arm

One new step in `smoke.yml`, running under `xvfb` — headless has no GL context
and every renderer read returns `(no webgl)`, which is how an earlier
measurement reached a wrong conclusion.

Scenario, exactly as the issue body states it:

1. `AsyncCamoufox()` with **no** `os=` argument.
2. Three contexts from that one browser via
   `AsyncNewContext(browser, os='macos' | 'windows' | 'linux')`.
3. Per context record `navigator.platform`, `UNMASKED_RENDERER_WEBGL`, and
   marker-font presence for all three OS marker sets.

Green means each context's platform, renderer and font set are mutually
coherent and differ from the other two contexts'.

### Controls

Per CLAUDE.md lesson 4, a reference is only a control if something guarantees
it can differ. The arm reports **setup-invalid**, not green, unless both hold:

- the three contexts differ from each other on at least one recorded signal, and
- a deliberately absent family reads absent in every context.

### Outcomes

- **Green** — close #44 citing the run id, and file the "still ungated after
  round 3" list from CLAUDE.md as separate issues:
  `CoreTextFontList::FindSystemFontFamily`, the DWrite non-shared substitution
  branch, the non-shared `LookupInFaceNameLists` / `CommonFontFallback` `else`
  branches, `LookupLocalFont` on the macOS and Windows platform font lists, and
  the context-0 fail-open.
- **Red** — report the failing signal, which names round 4. Do not write a fix
  in this pass. CLAUDE.md's own history is that a fix designed against a
  half-understood mechanism is how this issue got its first wrong conclusion.

Either way, state that a Linux measurement says nothing about macOS or Windows
host behaviour.

### Cost

`smoke.yml` is `workflow_dispatch` over an existing build artifact, so this
needs no new build. Use the most recent successful `main` build,
run `34450188525` — read the run list back before quoting it in a pull request
body rather than quoting it from here.

## Cross-cutting conventions

- Every pull request is tied to its issue and carries evidence: command output
  with exit status, run ids, and the decisive log lines. Never claim a pass
  without the output behind it.
- `gh run view --log` truncates long smoke logs with no marker. Read job logs
  with `gh api --allow-escape-sequences` on the job id.
- Any sha, run id or output excerpt that goes into a commit message, an issue or
  a pull request body is read back from the actual state first, not quoted from
  memory.
