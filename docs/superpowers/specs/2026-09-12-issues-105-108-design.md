## #105 — the font gate fails open at context 0

### What the code says the issue is

`CamouIsFontAllowed` (`patches/font-list-spoofing.patch`, applied at
`gfxPlatformFontList.cpp:1248`) answers `true` when the thread-local context id is
0 or has no per-context list. That is only a leak at call sites that ask
**nothing else**. Most sites already pair the per-context gate with the launch mask,
`MaskedFontListBlocks(aFontVisibilityProvider, key)` (`:918`), which consults
`MaskConfig::IsFontAllowed` through the document's `FontVisibilityProvider`, exempts
chrome documents and null providers, and never reads the thread-local context:
`FindAndAddFamiliesLocked` (`:1283`), the walk at `:1543`, `GlobalFontFallback`
(`:1831`, `:1877`), and `:2152`/`:2160`. Under a launch `fonts` list those sites
refuse a masked family whatever the context id is.

The sites that ask the per-context gate **alone** are:

- `CommonFontFallback` (`:1653`; gate at `:1713` in the non-shared branch, and the
  matching shared-list branch above it). Reached from `SystemFindFontForChar`
  *before* `GlobalFontFallback`, with `aFontVisibilityProvider` in scope. On Linux
  `gfxPlatformGtk::GetCommonFallbackFonts` (`gfxPlatformGtk.cpp:419`) lists
  Twemoji Mozilla first for emoji presentation, then DejaVu/FreeSans/Symbola/Noto
  Sans Symbols(2). `TwemojiMozilla.ttf` ships in `bundle/fonts/linux`, and the Linux
  package bundles all three font dirs (`Makefile:167`), so on CI a bare context can
  reach Twemoji through this path no matter what the launch list says.
- `GetFontList` (`:1393`; gate at `:1409`/`:1427`). Only the chrome font enumerator
  (`gfxPlatform::GetFontList` → `nsThebesFontEnumerator`) calls it; no page path.
  Not measured, left alone.
- `GetFontFamilyList` (`:1441`; gate at `:1450`), called from `gfxTextRun.cpp:2332`.
  Read during the plan; paired the same way if a provider is in scope there,
  otherwise documented as gated-by-reading only.

Who really runs at context 0: chrome documents, and every
`launch_persistent_context` session — `pythonlib/camoufox/sync_api.py:126` /
`async_api.py:130` return the persistent context without the fingerprint init
script, so it never gets a per-context list and relies on the launch mask alone.
The two `AutoFontListContext camouUnfiltered(0)` scopes (`:2806`, `:2817`) rely on
allow-all on purpose.

### Decision

**Superseded by the measurement below.** The pairing described here was the fix
planned for the RED outcome; runs 34692963764 through 34698688879 read the
predicted outcome (refused), so no browser code changed (PR #111). It stays as the
record of what would have been done, and of why "deny at 0" was rejected.

Do **not** change `CamouIsFontAllowed`. Denying at 0, or answering with the launch
mask at 0, would apply the mask to chrome documents at the unpaired sites (the gate
has no provider, so it cannot exempt them — on Windows that is the titlebar's Segoe
Fluent Icons). Instead **pair `CommonFontFallback` with `MaskedFontListBlocks`** in
exactly the shape `GlobalFontFallback` uses: hoist
`const bool maskedFontList = MaskedFontListAppliesTo(aFontVisibilityProvider);`,
and in both loops refuse a family when
`maskedFontList && MaskedFontListBlocks(aFontVisibilityProvider, key)` before asking
`CamouIsFontAllowed`. That covers context 0 (persistent contexts), bare
`new_context()` contexts, and any hop that fails to 0, for the launch-mask half,
while keeping the chrome exemption.

Residual, stated in the PR and in CLAUDE.md lesson 5: a context that *did* set a
per-context list but whose context id resolves to 0 gets the launch mask instead of
its narrower list. No hop is currently known to fail (arm (g) fixed
`OffscreenCanvas`; #83 was a cache, not a hop). A non-zero sentinel for "unresolved"
is not built — YAGNI until a failing hop is observed.

### Measure RED before writing any C++

The measurement decides whether there is a code fix. A new block in the big smoke
step, next to the `#101 GUARD`, four launches of ~10 s each, all under the pinned
Linux fontconfig (lesson 8 — state the `[launch]` line). Same JS in every launch:
a canvas rendering U+1F600 in `48px "NoSuchFamilyAtAll5"`, returning the pixel
checksum the way `PIXEL_JS` does, plus four log windows read from a mark taken
before the launch: `(textrun-systemfallback-common|global) char: u+01f600 ...
match: [Name]` (`gfxPlatformFontList::SystemFindFontForChar`), `CAMOU-FL gate`
(needle `twemoji`), `CAMOU-FL pref-fallback`, and `CAMOU-FL default-unfiltered`.
The verdict rule is the corrected one under "Validity and verdict" below.

| launch | context | role |
|---|---|---|
| L1 `CAMOU_CONFIG={}` | bare `new_context()` | reference for "resolved": Twemoji Mozilla allowed and served (pref-fallback line; no system-fallback line — see below) |
| L3 `{"fonts": FONTS["mac"]}` | `setFontList(FONTS["mac"])` | discriminator (`L1 != L3`) and refusal-shape reference (`match: [<none>]`); not a pixel floor — see below |
| L2 `{"fonts": FONTS["mac"]}` | bare `new_context()` (ctx ≥ 1) | question A |
| L2p `{"fonts": FONTS["mac"]}` | `launch_persistent_context(tmp user_data_dir)` (ctx 0) | question B — #105's headline |

`FONTS["mac"]` (525 names since #107) contains neither `Twemoji Mozilla` nor any
other family in the Linux common-fallback list.

Validity and verdict (lesson 4), as corrected after runs 34692963764 and
34693684958 (both build 34578327006):

- The spec first predicted `match: [Twemoji Mozilla]` on a system-fallback line
  for L1. That line never comes: `font.name-list.emoji` (all.js:2067) lists
  Twemoji Mozilla, so `gfxFontGroup::WhichPrefFontSupportsChar` serves U+1F600
  before `SystemFindFontForChar` runs, logging `CAMOU-FL pref-fallback ctx=6
  key=twemoji mozilla allowed=1` and nothing else. L1's evidence is that line plus
  its checksum.
- The spec first scored "refused" as equality with L3's checksum. That was never
  achievable: `GetDefaultFontLocked`'s #88 block answers from the context's own
  list only when `HasFontList(ctx)`, so a listed context (L3) and a listless one
  (L2, L2p) draw their notdef box with different default families and different
  pixels whether or not anything leaked (run 34693684958: L3 107971384, L2 = L2p
  524399160). L3 is a valid discriminator (`L1 != L3` proves the mask changes the
  output) but not a floor.
- A pixel floor cannot exist at all, in any context. Run 34696033492 (branch `meas/105-bare-under-mask` at `69504de`, build
  34578327006, conclusion `failure` — SETUP-INVALID by design) tried one
  (U+E000 drawn on the same canvas in the same context) and every launch read a
  different value for it than for U+1F600 (L3 107971384 vs 3482689396; L2
  524399160 vs 837171717). The mechanism is structural: a missing glyph is drawn
  by `gfxFontMissingGlyphs::DrawMissingGlyph` (`gfxFontMissingGlyphs.cpp:492-510`,
  from `gfxFont::DrawMissingGlyph`) as a hexbox carrying the codepoint's own hex
  digits, sized from the run's current font metrics — so two codepoints never
  draw the same pixels, and the same codepoint draws differently under different
  default fonts. `524399160` is the U+1F600 hexbox in a listless context's default
  metrics, not a third face.
- Refusal is therefore read from the browser's own lines, not from pixels. Per
  L2 and L2p: `emoji != L1.emoji`, **and** the launch's `(textrun-systemfallback-…)`
  window for u+01f600 is non-empty and every line reads `match: [<none>]`
  (`SystemFindFontForChar` ran, so nothing earlier served, and found nothing),
  **and** no leak line (next bullet). Validity: `L1.emoji != L3.emoji`; L1 has a
  `pref-fallback` or `gate` line `key=twemoji mozilla allowed=1` (twemoji was
  allowed; that it served is inferred from L1's empty system-fallback window and a
  checksum distinct from every masked launch); L3's system-fallback window reads
  `<none>` throughout. Any failure registers `unmeasured_arms["(ctx105)"]` and a
  `(ctx105) unmeasured` tripwire so the step goes SETUP-INVALID.
- Leak, per L2 and L2p: `emoji == L1.emoji`, or any `CAMOU-FL pref-fallback` or
  `CAMOU-FL gate` line in that launch's window with `allowed=1` whose family is not
  in the mac list. The `gate` window shows whether *any* gate allowed Twemoji under the mask — a
  gate line carries no call-site tag, so it cannot say which gate was asked.
  `CamouIsFamilyAllowed` asks `MaskedFontListBlocks` first and short-circuits, so
  a `key=twemoji mozilla allowed=1` gate line under the mask means the launch mask
  did not block it; an empty window plus a `<none>` system-fallback line means the
  mask refused first. The arm assumes `gfx.e10s.font-list.shared` is true (the
  shared branch of `CommonFontFallback` is the live one) and does not read it back.
  `bundle/fonts/linux` ships three families in this chain — Twemoji Mozilla, Noto
  Sans Symbols, Noto Sans Symbols2 — none mac-allowed; the gate needle sees only
  the first, the system-fallback and pref windows see all three. Every
  `CAMOU-FL default-unfiltered` line in any window is its own tripwire.
- What this arm cannot see: it runs under the pinned Linux bundle conf. A shipped
  mac session runs the macOS conf, where Apple Color Emoji serves U+1F600
  legitimately and would mask a Twemoji leak; GREEN here is a statement about the
  Linux conf only. `bundle/fonts/macos/AppleColorEmoji.ttf` ships and is
  mac-allowed, yet system fallback reported `cmaps: 0` in run 34693684958 — not
  explained, outside #105, stated as unmeasured.

Outcomes, before the run:

- **L2 or L2p leaks** → RED reproduced, `CommonFontFallback` is the target, fix as
  above.
- **Both refused** → no code fix. This is the **predicted** outcome: a second
  reading found that the shared-list branch of `CommonFontFallback` (the live one
  on Linux, `gfx.e10s.font-list.shared` true) looks families up through
  `FindSharedFamily` → `FindAndAddFamiliesLocked` → `CamouIsFamilyAllowed`
  (`:1268`), which is paired; the unpaired gate at `:1713` is the dormant
  non-shared branch CLAUDE.md already lists. The deliverable is then the arm kept
  as a guard, a correction to lesson 5, and #105 closed with the run quoted: the
  launch mask is provider-based and reaches every live site whatever the context
  id; what context 0 cannot have is a per-context list, and it cannot because
  chrome documents share id 0. Branch `fix/105-ctx0-guard`, no build.
- **Unmeasured** → fix the arm before anything else; a guard that measured
  nothing registers both `unmeasured_arms["(ctx105)"]` and a `(ctx105) unmeasured`
  tripwire so the step goes SETUP-INVALID rather than silently green.

The measurement runs on build **34578327006** (branch `fix/95-cmap-unicode-ucs4`,
same patch set as `main` since `f0072fc`), from a branch `meas/105-bare-under-mask`
carrying only the arm (diagnostic prints, nothing asserted).

### The fix, if RED reproduces (not predicted)

Branch `fix/105-common-fallback-launch-mask` off `main` `7feb5f9`, carrying the arm
plus the patch change. The patch is edited by regenerating `font-list-spoofing.patch`
whole from the applied tree (never a hand-edited hunk), dry-run with
`patch -p1 --forward -l --binary --dry-run` against the pristine tree. Regeneration
normalises the patch's pre-existing off-by-one last hunk; the PR says so.
`build.yml` is dispatched on the branch; its run id and branch go in the PR body
next to 34578327006's.

GREEN on the new build: L2 and L2p read as refused, L1 and L3 unchanged. Everything
the change did not touch must read the same as on `main`'s confirmation run
34688960474: arm j2's `ctx=6 resolved=.LastResort` (bare context, `CAMOU_CONFIG={}`,
`MaskConfig::IsFontAllowed` returns true on an empty list, so the empty-config case
is deliberately unchanged), `(cmap95)`, `(dot101)`, the `#44 contract guard`,
`default-unfiltered` at 0. The arm then becomes a guard: a leak registers
`tripwires.append("(ctx105) ...")`, never an inline assert (lesson 9's corollary).

Both suites are required for a `patches/` change: `build-tester` on the new binary
(headful, `run_tests.sh`), and `pythonlib.yml`.

## #108 — local pytest reaches the browser download

### Decision

Add `pythonlib/tests/conftest.py` with one autouse fixture that monkeypatches
`pkgman.CamoufoxFetcher.install`, `pkgman.CamoufoxFetcher.fetch_latest`,
`pkgman.GitHubDownloader.get_asset`, `pkgman.webdl` and `pkgman.requests.get` to
raise `RuntimeError("test reached the browser fetcher; mock it (#108)")` — superseded
by `pytest.fail(...)` in the #110 section below, for the reason given there. No test
mocks `requests` at the adapter level (grep of `pythonlib/tests` for `responses`,
`requests_mock`, `requests.Session`, `requests.get`: none), so raising on
`requests.get` breaks nothing that is currently correct. Tests that replace
`pkgman.CamoufoxFetcher` with a stub (`test_version_floor_upgrade.py`) are
unaffected: their stub is not the patched class.

Then run `pytest tests/ -q` from `pythonlib/` on this host. A test that reaches the
fetcher through `pkgman` fails with that message and #108's "which test" question
answers itself. One path does not: `addons.py:56` calls `webdl` through its own
import-time binding, the refusal surfaces from `pkgman.requests.get` inside the
`try` at `addons.py:88-97` and is swallowed and printed — that is #110, out of scope
here. Fix **that
test's** mocks, not the fixture. If more than one test trips, fix each.

### Evidence

- Local suite output, full pass, on this host — the first time it is usable here.
- CI `pythonlib.yml` on the branch, count ≥ 311 passed / 6 skipped (the count after
  #104).
- After the run, `~/Library/Caches/camoufox/browsers` does not exist and no
  `python` process holds a socket to `github.com` (`lsof -a -i -c python`). That
  check cannot see the uBlock Origin path (`addons.mozilla.org`, #110).
- #108's candidate list replaced by the actual test name(s) in the PR body.

## #110 — the addon download path, and why the guard's exception changes

Found by the final review of #109: `addons.py:56` downloads uBlock Origin through
`webdl`, the refusal from `pkgman.requests.get` surfaces inside the `try` at
`addons.py:88-93`, and `except Exception` at `:94` prints it and continues. 24
reaches per local run (23 tests; two further prints come from `test_addons.py`'s own
simulated failures and never touch the network), 0 tests failed by them; each attempt also created and removed
a directory in the real user cache (`addons.py` binds `INSTALL_DIR` at import, so
`utils.INSTALL_DIR` redirects do not move `ADDONS_DIR`).

### Decision

- `addons.py:94` stays. Continuing without uBO when offline is product behaviour.
- The guard's `_refuse` raises through `pytest.fail(...)` instead of `RuntimeError`.
  `_pytest.outcomes.Failed` derives from `BaseException`, not `Exception`, so it
  escapes that `except` and any other `except Exception` between the network call
  and the test. This supersedes the `RuntimeError` the #108 section mandates. The
  four `except BaseException` handlers in `sync_api.py` / `async_api.py` all
  re-raise, so nothing swallows it there. No extra patch target is needed: the addon
  path already dies at `pkgman.requests.get` inside `webdl`.
- The same fixture sets `addons.ADDONS_DIR` to `tmp_path / "addons"` (read at call
  time by `get_addon_path`): with `Failed` escaping, the `rmtree` at `:96` no longer
  runs, so without this every trip would leave `<user cache>/camoufox/addons/UBO`
  behind (`~/Library/Caches` on this macOS host, `~/.cache` on Linux CI).
- Tests that reach the addon path through `launch_options()` stub it at the call
  site with the idiom already in the repo — `monkeypatch.setattr(utils,
  "add_default_addons", lambda *_a, **_k: None)` (`test_humanize.py:22`,
  `test_launch_environment.py:13`) or `exclude_addons=[DefaultAddons.UBO]`
  (`test_seed_pinning.py:99`) — starting with the three helpers that already stub
  `get_path`. Not a fixture-level no-op of `add_default_addons`: that would make the
  path unreachable by construction and the guard blind to it. Not a patch of
  `maybe_download_addons`: `test_addons.py` calls it directly in six correct tests
  (three through the module attribute, three through a direct import binding).
- One test proves the swallow is escaped: under the fixture,
  `maybe_download_addons([DefaultAddons.UBO], [])` raises `pytest.fail.Exception` —
  through `maybe_download_addons`, so `addons.py:94` is on the stack; a direct call to
  `download_and_extract` would only prove the exception type.
- The `conftest.py` docstring paragraph "What this cannot see: the uBlock Origin
  addon download …" is deleted; it is no longer true.

### Evidence

Local suite green with no `~/Library/Caches/camoufox/addons` after `rm -rf` and a
full run; CI `pythonlib.yml` ≥ 314 passed / 6 skipped (`main` is 313 / 6 after #109
plus the new test). A green suite is now a positive statement that no test reached
a network call.
